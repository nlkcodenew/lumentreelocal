# 2026-05-17 Write Authorization Flow

This document defines the authorization model for any future Home Assistant
feature that can change inverter settings through the ESP32 BLE gateway.

The current production system remains read-only. Firmware only sends Modbus
function `03` read-register requests. No BLE write path is approved by this
document.

## Decision

`Device ID` is enough for read-only telemetry. It is not enough for write
permission.

Write permission must be granted through the ESP32 gateway because the gateway
is the physical device near the inverter and the only component with BLE access.
The public API must not mint write credentials only because a client knows an
inverter `Device ID`.

## Threat Model

Assume the following can happen:

- A stranger may know or guess an inverter Device ID.
- A Home Assistant instance may be misconfigured or exposed.
- The public API is reachable through `https://lumentree.jonah.io.vn`.
- Read-only telemetry can be low-risk, but inverter setting writes can affect
  battery, grid, backup, and persistent configuration behavior.

Therefore, write access needs an explicit possession or proximity signal from
the ESP32 gateway, not just a cloud/API lookup.

## Target User Flow

1. User flashes ESP32 firmware.
2. ESP32 opens AP `Lumentree-XXXX` if Wi-Fi is not configured.
3. User enters Wi-Fi credentials in the ESP32 portal.
4. ESP32 connects to Wi-Fi, stops AP, pairs to the inverter, and uploads
   read-only telemetry.
5. User installs Home Assistant integration `Lumentree Local`.
6. User enters only Device ID in HASS, for example `P240819130`.
7. HASS receives read-only entities. All write-capable entities stay disabled
   or unavailable.
8. If the user wants write access, the user opens the ESP32 portal and presses
   `Generate write pairing code`.
9. ESP32 creates a short-lived, one-time write pairing code.
10. User enters that code into the HASS integration options.
11. HASS sends the code to the API.
12. API validates that:
    - the gateway is online,
    - the gateway is associated with the requested Device ID,
    - the code exists,
    - the code is not expired,
    - the code was not already consumed.
13. API creates a scoped write grant for that Device ID and returns a grant
    token to HASS.
14. HASS stores the grant token in the config entry.
15. HASS enables only the approved write-capable controls.

## ESP32 Portal Role

The ESP32 portal is the authority for granting write access.

The portal already exists at `http://192.168.4.1` while AP mode is active. In
production STA mode the AP is stopped after Wi-Fi connects, so write
authorization needs one of these portal access paths:

- Short-term first implementation: user starts AP mode manually, then opens
  `http://192.168.4.1`.
- Better later implementation: ESP32 also serves the same portal on its LAN IP
  while connected to Wi-Fi.

The first implementation should be the short-term AP path because it keeps the
security model simple and requires physical/user intent near the gateway.

Portal page:

- `Write Access`
- button: `Generate write pairing code`
- display: one-time code and expiry timestamp
- status: current write grant state if known
- warning: read-only telemetry continues without write access

## Pairing Code Rules

The write pairing code must be:

- generated by ESP32,
- short-lived, recommended `5` to `10` minutes,
- one-time use,
- scoped to the configured `gateway_id` and `device_id`,
- never logged in plaintext by the server,
- invalidated after use or expiry.

The code is not the permanent write credential. It is only proof that the HASS
user had access to the ESP32 portal during the authorization window.

## API Responsibilities

Add a write grant subsystem separate from read-only telemetry.

Recommended tables:

- `lumentree_write_pairing_codes`
- `lumentree_write_grants`

Recommended `lumentree_write_pairing_codes` fields:

- `id`
- `gateway_id`
- `device_id`
- `code_hash`
- `expires_at`
- `consumed_at`
- `created_at`
- `created_by_firmware`

Recommended `lumentree_write_grants` fields:

- `id`
- `gateway_id`
- `device_id`
- `grant_token_hash`
- `scope`
- `enabled`
- `created_at`
- `revoked_at`
- `last_used_at`

API endpoints:

- `POST /api/lumentree/gateways/{gateway_id}/write-pairing-code`
  - called by ESP32 only
  - creates or rotates a short-lived code
- `POST /api/lumentree/devices/{device_id}/write-grants/claim`
  - called by HASS
  - accepts the user-entered pairing code
  - returns a scoped write grant token on success
- `GET /api/lumentree/devices/{device_id}/write-grants/status`
  - called by HASS
  - reports whether write is available/enabled/revoked
- `POST /api/lumentree/devices/{device_id}/write-grants/revoke`
  - called by HASS or admin
  - revokes write permission

The API must never expose the production API token or raw server secrets to
HASS.

## HASS Responsibilities

Home Assistant setup remains simple:

- API URL
- Device ID

No UUID, BLE MAC, or production API token should be required in the normal flow.

Add options flow:

- `Write access status`
- `Enter write pairing code`
- `Revoke write access`

Add entities:

- `sensor.write_access_status`
- `binary_sensor.write_grant_active`
- optional `switch.allow_inverter_writes`

The write switch should not create a grant by itself. It should only enable or
disable local HASS write controls after a valid grant exists.

## Firmware Responsibilities

Firmware must remain read-only by default.

Add only the authorization support first:

- generate one-time write pairing code,
- publish code hash or proof to the API,
- show plaintext code in the ESP32 portal,
- expose expiry/countdown in portal,
- keep command polling in dry-run mode until a real command is separately
  approved.

Do not add Modbus write functions as part of the authorization task.

## Write Command Gate

Even after a valid write grant exists, real write commands still need all gates
from `docs/plans/2026-05-17-write-safety-plan.md`:

- semantic command whitelist only,
- no raw register write service,
- API validation,
- firmware validation,
- pre-read,
- exact whitelisted write,
- post-read verification,
- Postgres audit trail,
- no indefinite retries.

Authorization answers "who is allowed to request a write." It does not answer
"which write is safe." Each write command still needs separate protocol
evidence and explicit approval.

## Explicit Non-Goals

- No real inverter setting write.
- No raw Modbus write service.
- No automatic write permission from Device ID alone.
- No hardcoded admin password in firmware.
- No permanent plaintext token shown in the ESP32 portal.
- No dependency on the vendor cloud for write permission.
